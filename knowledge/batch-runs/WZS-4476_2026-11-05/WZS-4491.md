## Bug card
- **Tenant / URL:** twos.wizcommerce.com (from the parent batch; the ticket names no URL), any page › header search icon (wiz_v2_search_icon 60badaa) › search modal (wiz_v2_search_modal e6f16b4, header doc 11995). Prod.
- **Expected:** With the iOS keyboard open, the search panel resizes or scrolls so Recent Searches, Recent Products and Top Results stay visible above the keyboard.
- **Actual:** That content is cut off or hidden behind the keyboard and Safari's floating address bar (recording ~0:11–0:20).
- **Repro:** Open search on iPhone Safari › focus the input (keyboard opens) › scroll the recent items or results.
- **Device / state:** iOS Safari, mobile; logged-in state not stated. Attachment: frame_0020s.jpg (not viewed).

## Root cause
- **Widget CSS:** In `storefront-wp/wp-content/mu-plugins/widgets/v2/SearchModalV2/style.css:909` (@media max-width:768px), `.wiz-search-modal` is `position:fixed; height:100dvh`.
- **Header CSS:** The header doc's CSS (post-11995.css) sets the scroll container `.wiz-search-content` to `max-height: calc(100dvh - 100px)` and a min-height of `calc(100dvh - 65px)`.
- **Why that fails on iOS:** iOS Safari draws the on-screen keyboard over the layout viewport. `dvh` only follows the URL-bar show/hide and doesn't shrink for the keyboard. So the panel stays full-screen tall, and the last part of its scroll range ends up under the keyboard.
- **Missing JS:** `search-modal.js` has no `visualViewport` resize/scroll handling. `git grep visualViewport|keyboard` on SearchModalV2 at master returns nothing.
- **Why it isn't an Elementor fix:** No CSS unit or widget control can track the iOS keyboard height. The widget has no height control (`tools/widget-controls.sh wiz_v2_search_modal`).

## Fix plan
- (not applied in auto mode, because this is a code bug)
- Suggested change in `search-modal.js`: while the modal is open on mobile, listen to `window.visualViewport` `resize`/`scroll` and set `--wiz-vvh: ${visualViewport.height}px` (and the offset top) on `.wiz-search-modal`.
- Suggested change in `style.css` (mobile block): use `height: var(--wiz-vvh, 100dvh)` for the modal, and make the inner scroll area `flex:1; min-height:0; overflow-y:auto` instead of fixed dvh max/min-heights.
- Then drop or relax the header doc's `calc(100dvh - 100px/65px)` overrides on twos.

## Jira comment
**RCA:** On mobile, the v2 search modal (`SearchModalV2/style.css:909`) is sized with `height: 100dvh`, and its results area uses dvh max-heights. iOS Safari doesn't shrink `dvh` when the keyboard opens, because the keyboard overlays the page. So the bottom part of the search panel (recent searches, recent products, top results) sits behind the keyboard and Safari's address bar. The widget's JS doesn't use `window.visualViewport` to adjust for the keyboard, and no Elementor setting can do it.

**Solution (FE code, storefront-wp):**
- In `SearchModalV2/search-modal.js`, while the modal is open on mobile, listen to `visualViewport` resize/scroll and set a CSS variable with the visible height on `.wiz-search-modal`.
- In the mobile CSS, size the modal with `height: var(--wiz-vvh, 100dvh)` and let the content area flex/scroll inside it (`flex:1; min-height:0; overflow-y:auto`) instead of fixed dvh heights.
- After that, review the twos header (doc 11995) search CSS overrides that also use `100dvh`.
- Verify on iPhone Safari: open search, focus the input, scroll to the last recent item or result. It should stay above the keyboard.
