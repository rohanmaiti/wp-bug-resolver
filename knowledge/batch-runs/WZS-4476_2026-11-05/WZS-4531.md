summary: Root cause found: the Publitas catalog's product popup loads the WP PDP (?hide=true, body.pdp-hide-chrome) inside the /catalogs/ page, and that PDP loads accessiBe again, so a second trigger shows. Fix is one kit #6 Custom CSS rule, tested live. Not applied because the Elementor editor redirects to wp-login.

## Bug card
- **Tenant / URL:** twos.wizcommerce.com/catalogs/ › open a catalog (flipbooks_widget f2b2930, Publitas iframe view.publitas.com/twos-company/…) › click a product (e.g. Glass Heart Decor / Paperweight Unit, SKU 56072) → PDP popup. Prod.
- **Expected vs actual:** Expected one accessibility (accessiBe) button. Actual: two blue accessibility person icons stacked/overlapping at the bottom-left.
- **Repro:** Catalogs → open a catalog → click a product to open its PDP popup → look at the bottom-left.
- **Device / login:** Desktop (screenshot); logged-in state not stated (doesn't matter).
- **Attachments:** catalogs-duplicate-accessibility-buttons.jpg (not viewed).

## Root cause
accessiBe is injected site-wide outside the code repo (no `acsb`/`accessibe` in storefront-wp; inline loader in HEAD + `acsbapp.com/apps/app/dist/js/app.js`), and it loads once on /catalogs/. When a Publitas product is clicked, Publitas opens the WP PDP `/product-details/<id>/?hide=true&token=…` in a nested iframe (ProductDetailsPage.php:85-104, which adds `body.pdp-hide-chrome`). That PDP page loads accessiBe a second time and draws its own trigger at the iframe's bottom-left, on top of the parent page's trigger. Reproduced by embedding the PDP with ?hide=true over /catalogs/: the iframe has its own `access-widget-ui` with `part="acsb-trigger"` (45×45 at bottom-left) next to the parent's.

Tested CSS (injected live into the embedded PDP):
- `body.pdp-hide-chrome access-widget-ui { display:none !important }` does **not** work, because accessiBe's shadow `:host` reset uses `!important` and wins.
- `body.pdp-hide-chrome access-widget-ui::part(acsb-trigger) { display:none !important }` **works**: the embedded trigger goes to `display:none` (0×0) and only the parent's button remains. The PDP iframe has `elementor-kit-6` and loads post-6.css, so kit Custom CSS applies there.

## Fix plan
1. Open Site Settings (kit #6): https://twos.wizcommerce.com/wp-admin/post.php?post=6&action=elementor → Site Settings › Custom CSS
2. Append (keep all existing CSS):
   ```css
   /* WZS-4531: hide the duplicate accessiBe trigger inside the flipbook PDP popup (?hide=true); the parent catalog page keeps its own */
   body.pdp-hide-chrome access-widget-ui::part(acsb-trigger) { display: none !important; }
   ```
3. Publish, then reload /catalogs/?nocache=… → open a catalog → click a product.
4. Check: one accessibility button at the bottom-left; it still opens the accessiBe panel. Normal PDPs (no ?hide=true) still show their button.

**Revert plan:** delete the two appended lines from kit #6 Custom CSS and publish.

## Verified
- (pre-test only) /catalogs/ with the PDP embedded at ?hide=true, desktop Chrome: the CSS injected into the embedded PDP hid its trigger; the parent trigger stayed visible.

## Flags
- Site-wide kit CSS, but scoped to `body.pdp-hide-chrome` (only set when the PDP is opened with ?hide=true, i.e. the flipbook popup).
- Tested on a PDP that 404s for a guest (the hide=true chrome is the same). Not tested inside the real Publitas popup, because it's cross-origin and needs a hotspot click.
- Trade-off: inside the popup, visitors use the parent page's accessiBe button, and its adjustments don't reach into the cross-origin popup content.
- Elementor editor redirected to wp-login.php?reauth=1 (WP admin session expired in Chrome).
