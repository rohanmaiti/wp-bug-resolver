summary: The forgot-password "user not found" error is a 404 UserNotFoundException raised by get_user_tenant_map() inside UserService.reset_password and never caught, so it escapes the endpoint's always-generic response. The storefront only shows the message the API returns. Nothing was changed.

## Bug card
- **Tenant / URL:** twos.wizcommerce.com/forgot-password/ (Two's Company). Prod.
- **Expected vs actual:** Expected the same result every time for the same email (or one generic success message). Actual: the same registered email (rythem.b+01@ / rythem.b+02@wizcommerce.com) sometimes shows "User not found" and sometimes sends the "Reset Your Password" email.
- **Repro:** Logged out or incognito → /forgot-password/ → enter the email → SEND RESET LINK → submit the same email again.
- **Device / login:** Desktop, logged out.
- **Attachments:** 4 frames + 1 screen recording (11:26 AM, Nov 5). One comment (Aryan Baliyan): "bug needs code change".

## Root cause
The storefront widget (`storefront-wp/wp-content/mu-plugins/widgets/auth/forgot-password.php:183-221`) calls `WizApi.call('password_reset')` → `POST /users/v1/password_reset`. On `.fail` it shows `err.data.message` as is, so the text comes from the backend.
The endpoint (`temp/api/user/v1/user.py:182-221`) is meant to always return a generic 200: it has a timing floor against account enumeration, and every "not eligible" branch in `UserService.reset_password` returns `None`.
But `reset_password` (`temp/api/user/services/user.py:1063-1067`) calls `get_user_tenant_map(str(user.id))`, which **raises** `UserNotFoundException` (404, message "user not found", `core/exceptions/user.py:28-31`) when it finds no `published` UserTenantMap rows (`user.py:1294-1297`). Nothing catches it, so it leaks to the browser as a 404 "user not found".
The intermittent part (same email, different result) wasn't proven here because no backend logs were checked. Likely causes: the mapping lookup has no tenant filter and no ordering, and `user_tenant_mappings[0]` is then compared with the request tenant (`user.py:1081-1082`), or the mapping read is inconsistent. The 404 leak itself is certain from the code.

## Jira comment
**RCA:** The forgot-password API sometimes throws a "user not found" error from its user-to-company lookup instead of returning its normal generic reply, and the storefront just shows that error. That is why the same email sometimes gets "User not found" and sometimes gets the reset email.

**API:** `POST /users/v1/password_reset` → 404 (intermittent; 200 otherwise). Payload: `{ "email": "rythem.b+02@wizcommerce.com" }`. Returns `message` = "user not found", expected a generic 200 (and the reset email for a valid user).

**Suggested fix:** `temp/api/user/services/user.py:1063`: in `reset_password`, catch `UserNotFoundException` from `get_user_tenant_map` and return `None`, so the endpoint always gives its generic reply. For WizShop, also look up the mapping by the request `tenant_id` instead of picking an unordered `[0]` (line 1081), so a valid user gets the email every time. Handed to the backend team.
