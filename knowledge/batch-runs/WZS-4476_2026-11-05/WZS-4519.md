summary: Header reads identity from localStorage UserDetails while the dashboard body is rendered from the server cookie. WizSessionSync's reconcile() repairs only logged-in/logged-out mismatches and deliberately skips "both present but different users", so a stale browser half (John) sits beside a server half for another customer (Zzzz Test Customer). This is a storefront-wp JS gap, and nothing was changed.

## Bug card
- **Tenant / URL:** twos.wizcommerce.com, Account Dashboard + header profile dropdown (Two's Company). Prod.
- **Expected vs actual:** Expected the header email, the territory manager and the dashboard customer to all match the active session. Actual: in Safari the header shows "Hello John / john@primejewellery.com" while the dashboard body shows "Zzzz Test Customer, Account #ZZZ0300004".
- **Repro:** Log in as User A in Chrome. Open Safari (which already has a different login) and go to Account Dashboard. Open the profile menu and compare it with the Welcome Back name and the territory manager.
- **Device / login:** Desktop Safari vs Chrome. Logged in (two different users).
- **Attachments:** 1 screenshot (image-c33ac082…png, Safari dashboard mismatch). No comments.

## Root cause
A login lives in two halves (`storefront-wp/wp-content/mu-plugins/helpers/js/wiz-session-sync.js:8-15`). The browser half is localStorage `UserDetails` + `persist:root`, and the header, WizApi and page JS read it. The server half is the `UserDetails` / `auth_access_token` cookies, and PHP reads it to render the dashboard body. `describeMismatch()` (`wiz-session-sync.js:794-800`) flags only cookie-without-token and token-without-cookie. The comment at lines 778-780 says "both present but for DIFFERENT buyers" is **deliberately not handled** (so a customer switch isn't undone). When the two halves belong to different users, which is the ticket's Safari state, nothing repairs it. The header keeps showing the stale localStorage user (John), and PHP renders the cookie's customer (Zzzz Test Customer, with its territory manager). Not reproduced live: it needs two different buyer logins and I can't type credentials. The classification rests on the code path. Not an Elementor issue, because the widgets just render whichever half they read.

Suggested direction (for the FE team, not applied): in `describeMismatch()`, also compare the user id in the cookie's `UserDetails` with `localStorage.UserDetails.id || user_id`, which the file already reads at around line 168. When they differ and `isWizOrderSwitchInProgress()` is false after the existing 1.5 s recheck, treat it as a mismatch and re-sync. The safe option is to log out both halves via `/session-logout` and reload, so the user signs in again. Another option is a server-side check: PHP emits the cookie's user id on the page and the header refuses to render a different localStorage identity.

## Jira comment
**RCA:** The storefront keeps a login in two places: the browser's localStorage (read by the header/profile menu) and a server cookie (used to render the Account Dashboard). Our session-sync script repairs the case where one is logged in and the other is logged out, but it intentionally skips the case where **both are logged in as different users**. In Safari the localStorage still held John (john@primejewellery.com) while the cookie was for Zzzz Test Customer, so the header and the dashboard showed different people.

**Solution (FE code, storefront-wp):** In `helpers/js/wiz-session-sync.js` › `describeMismatch()`, also compare the user id in the cookie with the one in localStorage `UserDetails`. If they still differ after the existing recheck and no customer switch is in progress, clear both halves (`/session-logout`) and reload so the user signs in cleanly. Then verify on twos.wizcommerce.com: log in as two users in Chrome and Safari, and check that the header email, Welcome Back name and territory manager always match.
